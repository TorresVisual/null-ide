# null-setup

`null-setup.exe` lives at `<installDir>\setup\null-setup.exe`. Modes: `prefetch` (headless download + SHA256 verify into `%LOCALAPPDATA%\Null\updates\<tag>\`, JSON progress lines on stdout), `update` (progress window; relocates itself out of the install dir, closes the IDE, journaled swap with rollback, re-applies registrations natively (`setup/core/src/shell/`), waits for the new IDE's `.null-ready` marker), `recover` (finishes or rolls back an interrupted swap from `<parent>\.null-update-journal.json`). `update` never elevates. `NULL_SETUP_API_BASE` redirects the GitHub API for tests (`scripts/fake-release.mjs`). Core logic and its tests are in `setup/core` (`cargo test -p null-setup-core`). Design `docs/specs/null-setup-installer-design.md`; plan `docs/plans/null-setup-updater.md`.

Installer engine (headless CLI modes; the wizard below is a window over the same code): `install --version <tag> --install-dir <dir> [--config <file>]` (refuses an existing install and a non-empty folder), `repair` (reinstall the installed version), `modify --config <file>` (registrations only → no swap and the IDE keeps running; a changed built-in set → repair with the new config) and `uninstall [--delete-data]` (keeps `data\` and `%APPDATA%\Null` unless asked; never touches a folder without `.null-ide-install.json`). All four go through the `update` pipeline (`update::Kind { Install, Update, Repair }`) or `manage`, print JSON progress lines, and `--force-close` ends IDE processes that ignore the close request. `<install>\install-config.json` (`install_config.rs`: shell-integration `Feature`s plus `excludedBuiltins`) is read by `update`, so updates honor the saved choices (an exclusion the new release cannot honor lapses with a log note; a corrupt or newer-schema file stops the update before anything is extracted). `<install>\builtins.json` is generated by `scripts/gen-builtins.mjs` from `setup/builtins.config.json` plus each extension's `package.json` and shipped in the zip and as a release asset; excluded built-ins are deleted from the staged tree before the swap (core ones are locked, dependencies via `requires` stay). Registrations are native (sub-project 2b, `setup/core/src/shell/`): `Registrar` (injected through `Opts`, `UninstallOpts` and `modify_in_place`, so tests never write the registry) → `shell::apply_with(loc, sys, …)` over a `Locations` (HKCU prefix + Desktop/Programs folders; tests use a scratch hive) and a `System` trait (Explorer, change broadcasts, `.lnk`, certificate store, APPX; faked in tests, `WinSystem` for real). The Win11 sparse APPX still goes through the three `*-AppxPackage` PowerShell cmdlets; the elevated certificate import is `null-setup trust-cert --install-dir <dir>` (reads only `<dir>\shell-ext\NullIDECert.cer`, requires `.null-ide-install.json` and subject `CN=Null IDE`). The PowerShell registration script and the Inno installer are gone; `shell/assoc.rs` is the only file-association table. Only `install` and `modify` may elevate. Plan `docs/plans/null-setup-registrations.md`; runbook `docs/specs/null-setup-registrations-runbook.md`. Run the four modes from a copy outside the install: started from `<install>\setup\null-setup.exe` the process relocates itself and exits 0 at once, so the caller sees neither the result nor the exit code (the relocated copy cannot be waited for, a handle on the original would block the swap). Plan `docs/plans/null-setup-installer-engine.md`; pruning check `docs/specs/builtin-pruning-check.md`; runbook `docs/specs/null-setup-installer-engine-test-runbook.md`.

First-run hand-over (sub-project 2c-1): `builtins.json` also carries a `settings` table (the seven keys the wizard may preset: `workbench.colorTheme`, `editor.fontFamily`, `editor.fontSize`, `files.autoSave`, `editor.formatOnSave`, `window.menuBarVisibility`, `null.updates.check`) and a `marketplace` table (empty); both come from `setup/builtins.config.json`. `install --first-run <abs file>` (install only) checks the choices against the installed package's `builtins.json` (`first_run::validate`) and writes `%APPDATA%\Null\null-setup\first-run.json`; nothing is written for an invalid or empty set. null-tools consumes it once (see its table). Plan `docs/plans/null-setup-first-run.md`; check `docs/specs/null-setup-first-run-check.md`.

Wizard (sub-project 2c-2): `NullIDESetup-<version>.exe` is a copy of `null-setup.exe`; with no arguments it opens the wizard (`Mode::Wizard`), which installs the newest stable release (`release::resolve_latest`, `builtins.json` asset as the manifest; a release without that asset hides the built-in and settings pages, a failed download shows an error page with Retry). Rules that need no window are in `core` (`wizard::decide` picks Install / Maintenance / Modify / Uninstall / Stale from `--intent` and the Add/Remove Programs entry; `webview2`; `shell::arp`); the window (`app/src/wizard.rs`, `ui/wizard*.{html,css,js}`) only collects choices and runs them through `cli::dispatch`, the same path as the headless modes, with the choices as temp files. `ui/wizard-model.js` holds the testable rules (`node --test setup/ui-tests/wizard-model.test.mjs`). The Add/Remove Programs key `HKCU\…\Uninstall\NullIDE` is written by every successful install/repair/update (`Registrar::arp`) and removed last by uninstall; its Modify/Uninstall commands are `"<install>\setup\null-setup.exe" wizard --install-dir "<dir>" --intent modify|uninstall`. Missing WebView2 shows a native dialog. **`Null: Setup`** (sub-project 2c-3; `null-tools/src/setupIntegration.ts`, Features launcher group *setup*) spawns `<install>\setup\null-setup.exe wizard --install-dir <dir> --intent modify` detached; there is no second UI. `install` saves `first-run.json` even when a registration warned (`cli::merge`). Plan `docs/plans/null-setup-retirement.md`. Plan `docs/plans/null-setup-wizard.md`; runbook `docs/specs/null-setup-wizard-runbook.md`.
