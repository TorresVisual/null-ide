# Null Accounts — Phase 7: Integration Implementation Plan

> **For agentic workers:** See Execution Options below — the checked Execution Mode box names the REQUIRED SUB-SKILL (superpowers:executing-plans or superpowers:subagent-driven-development).

**Goal:** Close out issue #102: each project card on the Null dashboard shows the account its folder is bound to, an end-to-end `verify-local` spec proves that binding a folder really wires git (and unbinding really undoes it), and the docs and compiled output say so.

**Architecture:** The dashboard (`null-tools`) asks the already-exported `NullAccountsApi.getAccountForFolder(uri)` for every recent project's path — bindings are keyed by path in `globalState`, so folders that are not open work too — and sends the result to the webview as one extra display string (`account`). A pure `dashboardAccounts.ts` owns the mapping and is unit-tested; `dashboard.ts` only wires it and re-sends the project list when the API's `onDidChange` fires. The integration spec runs in a real VS Code extension host: because no spec can sign in to a provider, `null-accounts` registers two test-only commands (add / remove an account) **only** when `context.extensionMode === ExtensionMode.Test`; the runner points git at a throw-away global config so the credential the spec approves lands in a temp file, not in Windows Credential Manager.

**Tech Stack:** TypeScript (strict), `node --test` + `node:assert/strict` (null-tools unit tests), Mocha `tdd` via `@vscode/test-electron` (integration, as `activation.spec.ts` already does), `git config --local`, `git credential` with the `store` helper.

**Spec:** `docs/specs/null-accounts-design.md` (issue #102), sections "Testing" and "Delivery phases" item 7. This is plan 7 of 7: (1) Foundation, (2) GitHub + binding, (3) UI, (4) Accounts menu, (5) GitLab, (6) Git wiring (`docs/plans/null-accounts-phase{1,2,3,4,5,6}-*.md`); (7) Integration ← this plan. **Phase 6 is planned but not executed at the time of writing: Task 1 and the docs of Task 3 stand alone, but Task 2's spec asserts Phase 6's behaviour and cannot pass until Phase 6 Tasks 1–5 are in the tree.** Execute Phase 6 first.

## Global Constraints

- Phase 1–6 constraints still hold: every `.ts` file starts with `'use strict';`; unit-tested modules do not import `vscode` at runtime (`import type` is fine); secrets only in `SecretStorage` and never logged; edit TypeScript sources only — `extensions/*/out/` and `extensions/null-tools/lib/*.js` are tracked but regenerated by `npm run compile` and committed alone in a `chore: refresh <ext> compiled output` commit (Task 3); commit after each task, message ends with `Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>`; do not push.
- Run unit tests with `npm --prefix extensions/null-tools test` and `npm --prefix extensions/null-accounts test` (each runs `tsc` first, then `node --test` over the files listed in `scripts.test`; a new test file must be appended to that list in the task that creates it). Integration specs run with the `verify-local` skill: `/verify-local null-accounts` (syncs the compiled extension into the installed Null IDE, then runs `npm --prefix extensions/null-accounts run test:integration` in a separately downloaded VS Code build).
- `null-tools` and `null-accounts` are built separately. `null-tools` reaches accounts **only** through `getAccountsApi()` (`extensions/null-tools/src/github/githubAuth.ts`) and the structural `AccountLike` / `AccountsApiLike` types in `githubSession.ts`; it never imports from `extensions/null-accounts/`.
- The spec run must never touch the developer's real git config or credential store. The only token in it is the fake `glpat-integration-spec-token`.
- **Deviations from the spec** (each one is applied to the spec in Task 3):
  1. The spec asks to "assert the Issues panel's token request resolves through the API". A GitHub token cannot exist in the test host (no GitHub session, no network), and the Issues-side logic (`resolveGithubSession`) is already unit-tested in `githubSession.test.ts`. The integration spec instead asserts that `api.getToken(account)` returns the stored token for a seeded GitLab access-token account — the very call `resolveGithubSession` makes.
  2. The spec asserts "credential keys" in the repo; the integration spec asserts those **and** that the token reached a credential store, using git's file-based `store` helper in a temp global config instead of the OS store (which stays a manual check, Phase 6 Task 8).
- Not in this phase: changing a project's account from its dashboard card (binding an unopened folder needs a per-folder picker that does not exist; the status bar, Accounts panel and Accounts menu still bind the open folder), filtering or sorting cards by account, suggesting an account after *Clone Repo* (would need `suggest()` on the public API), and any new `NullAccountsApi` method — account deletion stays off the API on purpose.

```ts
'use strict';

/** The slice of a null-accounts Account that a dashboard card shows. */
export interface AccountSummary { username: string; host: string }

/** "alice@github.com": the identity git and the Accounts panel show; one rule, no special cases. */
export function accountLabel(account: AccountSummary): string {
  return `${account.username}@${account.host}`;
}

/**
 * Adds `account` (a display label) to each project whose folder is bound to one. A `.code-workspace`
 * entry is a file, not a folder, so it never has a binding.
 */
export function withAccounts<T extends { path: string; isWorkspaceFile: boolean }>(
  projects: readonly T[],
  accountFor: (folderPath: string) => AccountSummary | undefined,
): Array<T & { account?: string }> {
  return projects.map(project => {
    const account = project.isWorkspaceFile ? undefined : accountFor(project.path);
    return account ? { ...project, account: accountLabel(account) } : project;
  });
}
```

Create `extensions/null-accounts/src/test/suite/gitWiring.spec.ts`:

```ts
'use strict';

import * as assert from 'assert';
import { execFileSync } from 'child_process';
import * as fs from 'fs';
import * as vscode from 'vscode';
import { NullAccountsApi } from '../../api';
import { Account, NewAccount } from '../../types';

// A GitLab access-token account: its token is the raw stored secret, so no provider or network is involved.
const NEW_ACCOUNT: NewAccount = {
  provider: 'gitlab', host: 'gitlab.example.test', username: 'spec-user', email: 'spec-user@example.test', authMethod: 'https',
};
const TOKEN = 'glpat-integration-spec-token';
const CREDENTIAL_KEY = `credential.https://${NEW_ACCOUNT.host}.username`;
const HAND_SET_EMAIL = 'me@work.example';

/** Output of `git <args>` in `cwd`; '' when git exits non-zero (an unset config key). */
function git(cwd: string, ...args: string[]): string {
  try { return execFileSync('git', args, { cwd, encoding: 'utf8' }).trim(); } catch { return ''; }
}

/** Wiring runs asynchronously after a bind or a removal, so poll instead of reading once. */
async function waitFor(what: string, done: () => boolean): Promise<void> {
  for (let i = 0; i < 100; i++) {
    if (done()) { return; }
    await new Promise(resolve => setTimeout(resolve, 100));
  }
  assert.fail(`timed out waiting for ${what}`);
}

suite('null-accounts git wiring', () => {
  test('binding wires the repo and the credential store; removing the account undoes both', async function () {
    this.timeout(30_000);
    const api = await vscode.extensions.getExtension<NullAccountsApi>('null.null-accounts')!.activate();
    const folder = vscode.workspace.workspaceFolders?.[0]?.uri;
    assert.ok(folder, 'the run opens a temp workspace folder');
    const repo = folder.fsPath;
    const credentialsFile = process.env.NULL_ACCOUNTS_SPEC_CREDENTIALS;
    assert.ok(credentialsFile, 'runTest.ts must set NULL_ACCOUNTS_SPEC_CREDENTIALS (else the run could hit the real credential store)');
    const stored = (): string => (fs.existsSync(credentialsFile) ? fs.readFileSync(credentialsFile, 'utf8') : '');

    execFileSync('git', ['init', '-q'], { cwd: repo });
    execFileSync('git', ['config', '--local', 'user.email', HAND_SET_EMAIL], { cwd: repo }); // must survive the round trip

    const added = await vscode.commands.executeCommand<Account>('null-accounts.test.addAccount', NEW_ACCOUNT, TOKEN);
    await vscode.commands.executeCommand('null-accounts.bindFolderToAccount', added.id);
    assert.strictEqual(api.getAccountForFolder(folder)?.id, added.id);
    if (process.platform === 'win32') {
      // recent-projects.json and the binding can spell one path differently; the lookup normalises both.
      assert.strictEqual(api.getAccountForFolder(vscode.Uri.file(repo.toUpperCase()))?.id, added.id);
    }

    await waitFor('the account to be written into the repo', () =>
      git(repo, 'config', '--local', 'user.email') === NEW_ACCOUNT.email
      && git(repo, 'config', '--local', 'user.name') === NEW_ACCOUNT.username
      && git(repo, 'config', '--local', CREDENTIAL_KEY) === NEW_ACCOUNT.username);
    assert.strictEqual(git(repo, 'config', '--global', 'user.email'), '', 'the global config must stay untouched');

    await waitFor('the token to reach the credential store', () =>
      stored().includes(`https://${NEW_ACCOUNT.username}:${TOKEN}@${NEW_ACCOUNT.host}`));
    // The call the Issues panel and every other consumer makes.
    assert.strictEqual(await api.getToken(added), TOKEN);

    await vscode.commands.executeCommand('null-accounts.test.removeAccount', added.id);
    await waitFor('the repo to be restored', () =>
      git(repo, 'config', '--local', 'user.email') === HAND_SET_EMAIL
      && git(repo, 'config', '--local', 'user.name') === ''
      && git(repo, 'config', '--local', CREDENTIAL_KEY) === '');
    await waitFor('the credential to be withdrawn', () => !stored().includes(NEW_ACCOUNT.host));
    assert.strictEqual(api.getAccountForFolder(folder), undefined);
    // Leaves the account list empty, as activation.spec.ts expects whatever order the specs run in.
    assert.deepStrictEqual(api.getAccounts(), []);
  });
});
```
