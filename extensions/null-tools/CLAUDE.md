# null-tools

Written in TypeScript (`src/`). Activated on `onStartupFinished`. Provides:

| Feature | Details |
|---|---|
| **Project dashboard** | Custom editor (`null.dashboard`, `viewType`); opened on startup and via Help > Welcome (see `patches/003-*` and `004-*`); recent-project cards with async git status, New Project, Clone Repo |
| **GitHub Issues panel** | Activity-bar view (`null-issues`), a full-width tab (`null.issues.openFullView`) and one tab per issue; GraphQL search, composer with per-issue drafts, image attach (committed to an orphan `null-issue-assets` branch, thumbnails cached in `.null/issue-images/`), *Copy as prompt*, and an "open this issue?" prompt when you switch to an `issue-<n>-…` branch. Signs in through null-accounts (`githubAuth.ts` → `githubSession.ts`); `null-tools` declares `extensionDependencies: ["null.null-accounts"]`. Webview code in `src/webview/` is compiled by separate `tsconfig.webview-*.json` projects into `lib/` |
| **Pull Requests** | `src/pulls/` (#92, phase 1 of #117): the `null.pullsView` tree in the `null-issues` container lists the 50 most recently updated open PRs (CI/draft icon from one GraphQL search); a PR expands to its changed files, which open in `vscode.diff` between the merge base and the head. File text comes from the Contents API through the `null-pr:` content provider (`pullContentProvider.ts`, URIs built and validated by `pullDocs.ts`), not from git. Review threads and new line comments use the Comments API (`pullReview.ts`; comments post at once, one line, until pending reviews land in phase 3). Checkout (`pullCheckout.ts`) fetches `pull/<n>/head` into the PR's head branch name (`pr/<n>` for a fork PR) and only ever creates or fast-forwards it. Gating reuses the commit graph's `classifyWorkspace`; the view's state is the `null.pulls.state` context key (test seam `_null.pulls.snapshot`). Files over 2 MB or binary open a placeholder. Pure: `pullModel.ts`, `pullDocs.ts`; `pullApi.ts` wraps `requestGraphql`/`requestJson`. GitHub only. Design `docs/specs/pull-requests-design.md`; plan `docs/plans/pull-requests-phase1-review.md`. Phase 2 (`docs/plans/pull-requests-phase2-detail-checks.md`): `pullFilter.ts` (pure: filter → GitHub search `q`, kept in `workspaceState` as `null.pulls.filter`, edited by `pullFilterMenu.ts`) and a detail tab (`pullDetailPanel.ts` + `pullDetailModel.ts`/`pullDetailApi.ts`; webview bundle `lib/pullDetail.js` from `src/webview/pullDetail*.ts`, HTML builders tested through `webview-shared`). Read-only except *Re-run failed jobs*, whose run ids the host recomputes from its own page; links from the webview open only as absolute https. |
| **Commit message generation** | `null.generateCommitMessage` (`Ctrl+Shift+Alt+G`) — runs `claude --print` with staged diff; sets SCM input box |
| **Commit message validation** | `commitValidation.ts` (pure Conventional Commits check) + `commitValidationIntegration.ts`: squiggles on the SCM commit box (`vscode-scm` docs) and the `null.commitMessage.check` command; `null.commitMessage.validation` = `off`/`warn` (default)/`strict`. Strict blocking needs patch 008 |
| **In-app updater** | Checks GitHub Releases on startup; shows status bar button; `null-setup prefetch` downloads in the background, the click runs `null-setup update` (no PowerShell, no staging code in the extension). Pure helpers in `updateStatus.ts`. On Linux the updater only checks for `null-ide-linux-x64-*.tar.gz` and opens the release page (`canSelfUpdate`); `nullDataDir()` is the per-OS Null user-data folder |
| **Discord Rich Presence** | `discordRpcClient.ts` (IPC pipe / WebSocket transport), `discordPresence.ts` (activity building), `presenceOwnership.ts` (one window publishes), `discordAppInfo.ts` (Developer Portal diagnostics). Configured via `null.discord.*`; `null.discord.testConnection` reports setup problems |
| **Null: Setup** | `null.setup.open` (`setupIntegration.ts`) opens the installer window on Modify; the same window handles Repair/Uninstall |
| **Crash recovery** | `src/recovery/` (#17). Unsaved editors come back through VS Code's own hot exit (`files.hotExit`/`window.restoreWindows` pinned in `product.json`). Each window writes `<pid>-<startedAt>.json` under `globalStorageUri/recovery` and deletes it on dispose; a marker with a dead pid is a crash and stays until the user reviews or discards it (`crashMarker.ts`). `interruptedSessions.ts` reads the head/tail of `~/.claude/projects/<workspace>/*.jsonl` written between the crashed run's start and this window's start and flags sessions whose last turn did not finish. `recoveryIntegration.ts` (only `vscode` file) shows Review / Later / Discard and opens sessions with `claude-vscode.editor.open`. Unsent prompts and interrupted operations cannot be recovered (the extension owns both). `null.recovery.enabled` is the master switch. Design `docs/specs/crash-recovery-design.md`; plan `docs/plans/crash-recovery.md` |
| **First-run choices** | `firstRun.ts` (pure, host injected) + `firstRunIntegration.ts` (the only `vscode` file): on activation reads `%APPDATA%\Null\null-setup\first-run.json` once. Only the seven allowlisted settings (`ALLOWED_SETTINGS`, pinned by a test to `setup/builtins.config.json`), only when the user has no global value (`inspect().globalValue === undefined`, so a user's `false` stays); extensions install one at a time with a 120 s timeout, failures give one notification with Retry. The file is deleted after processing; a failed settings write keeps it for the next launch, an unusable one is discarded. `null.updates.check` (default on) gates only the startup update check |
| **Null Workspace hub** | `featureRegistry.ts` (pure) + `featuresTreeView.ts`: the **Features** view at the top of the `null-workspace` container lists launcher entries that every `null.*` extension declares as a top-level `nullWorkspace.features` array in its own `package.json` (`id`, `label`, `command`, `category`, optional `icon` codicon / `description` / `order`); categories `develop` / `insights` / `account` / `setup` (unknown ones append). Entries are static; non-`null` publishers are ignored. `featureManifests.test.ts` checks every entry's command exists. Design `docs/specs/null-workspace-hub-design.md`; plan `docs/plans/null-workspace-hub.md` |
| **Commit graph** | `src/graph/` (#87): lane-drawn history in one reused tab (`null.graph.open`, `null.commitGraph`) and a collapsed list in the `null-workspace` container (`null.graphView`, first 50 commits). Acts on the first folder's own worktree (`git rev-parse --show-toplevel`), never the main worktree; nothing runs in remote windows or untrusted workspaces (welcome states via the `null.graph.state` context key). The host owns everything: pure `gitLog.ts` / `graphLayout.ts` / `graphMessages.ts`, `gitGraphService.ts` (paging with `--date-order` over `--branches --tags --remotes HEAD` plus stash SHAs, fingerprint, detail, files), `gitActions.ts` (`Result<T>`; cherry-pick/revert/continue/skip/abort, reset with impact counts), `gitRun.ts` (the only `execFile`: `GIT_OPTIONAL_LOCKS=0`, `GIT_EDITOR=true`, `BusyFlag`), `graphSession.ts` (shared service; the `vscode.git` change event only triggers a fingerprint check; runs actions one at a time). Only `graphSession`, `commitGraphPanel`, `graphTreeView`, `graphCommands`, `graphDiff`, `gitApi` and `graphIntegration` import `vscode`. Webview (`src/webview/commitGraph.ts`, `module: none`, compiled by `tsconfig.webview-commit-graph.json` into the tracked `lib/commitGraph.js`; `lib/commitGraph.css` is hand-written); its pure math is `commitGraphModel.ts`, loaded by tests through `webview-shared.js`. Context menus use `data-vscode-context` + `webview/context`, so one `null.graph.*` command set serves tab and tree; the key `null.graph.operationInProgress` disables them and a banner offers Continue/Skip/Abort. Internal test seams: `_null.graph.snapshot`, `_null.graph.dispatch`. Design `docs/specs/commit-graph-design.md`; plan `docs/plans/commit-graph.md`. Integration spec: `npm run test:integration` (via `/verify-local null-tools`) |
