# null-devcontainer

Quick-and-dirty dev containers. `extensionKind: ["ui"]` (runs on the machine with Docker); `enabledApiProposals: ["resolvers"]`, so `product.json → extensionAllowedProposedApi` lists `null.null-devcontainer`. Not in the REH server tarball (UI-side only).

Flow: `Null: Reopen in Container` opens `vscode-remote://dev-container+<hex(local path)>/workspaces/<name>`. `resolve` in `extension.ts` then: runs `initializeCommand` (via `sh -c`), `docker run -d` (name `null-dc-<sha1>`, entrypoint replaced by a sleep loop, workspace bind-mounted, `-p 127.0.0.1::33000`), downloads the Null server from `product.json → serverDownloadUrlTemplate` (cached in globalStorage) and `docker cp`s it into `~/<serverDataFolderName>/bin/<commit>`, installs the listed extensions with the server's `--install-extension` (once per container, marker `dc-exts`), starts the server on 0.0.0.0:33000 with a persistent token (process lookup in /proc by install path) and returns `ResolvedAuthority('127.0.0.1', <docker port>, token)`. Pure helpers (JSONC parse, variable substitution, authority encoding, run args) are in `devcontainer.ts` and covered by `npm test`.

Known gaps (deliberate): `image` only (no Dockerfile/compose/features), `updateRemoteUserUID` is ignored (the real extension skips it on Windows/macOS hosts too), no `forwardPorts`/`mounts`/`postCreateCommand`, config edits need `Null: Rebuild Container`, registry login (`docker login`) is the user's job. Verified by hand against `ubuntu:22.04` and the v1.0.23 `null-reh-linux-x64` tarball: server install, idempotent start, published port + token, and `--install-extension` (6 of the 7 example extensions; `mbehr1.vsc-webshark` is not on Open VSX). Not verified: the resolver inside a running Null IDE, and the TU Graz image (registry unreachable without VPN/login). `docker.exe` may not be on PATH in a shell; Docker Desktop keeps it in `%LOCALAPPDATA%/Programs/DockerDesktop/resources/bin`.

Git + null-accounts keys: null-accounts writes host paths (`core.sshCommand`, `user.signingkey`, `commit.gpgsign`) into the repo's `.git/config`, which the container shares through the bind mount, so inside the container signing fails with "Couldn't load public key C:/Users/…". Each resolve copies the host's `~/.ssh/null-accounts` into the container user's `~/.ssh/null-accounts` (chown + 600/700, which ssh requires) and starts the server with `GIT_CONFIG_*` env (command scope, beats the repo config; git >= 2.31) that repoints those two keys and adds `StrictHostKeyChecking=accept-new`. The env lives in `~/.null-server/dc-env`; a changed set restarts the server. Verified by hand in an `ubuntu:22.04` container: signed commit and `ssh -T` to the university GitLab. HTTPS credentials (the OS credential store on the host) are not forwarded.
