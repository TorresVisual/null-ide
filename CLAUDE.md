# CLAUDE.md

This file provides guidance to Claude Code when working with code in this repository.

## Project Overview

**Null IDE** is a custom Windows desktop code editor built on VSCodium (itself a fork of VS Code with Microsoft telemetry removed). It ships with its own binary name, branding, built-in extensions, and an automated GitHub Actions release pipeline.

Key characteristics:
- Binary name: `null.exe` — accessible from the terminal as `null .`
- Built on VSCodium, which strips Microsoft telemetry from VS Code
- Thirteen built-in extensions bundled at build time: `null-theme`, `null-icons`, `null-tools`, `null-markdown`, `null-cpp`, `null-actions`, `null-accounts`, `null-format`, `null-music`, `null-activity`, `null-startup`, `null-env`, `null-sync`
- **Code Spell Checker** (`streetsidesoftware.code-spell-checker`) bundled as a fourteenth built-in extension; version pinned via `CSPELL_TAG` env var in `build.yml`
- **Remote development** (#85): `jeanp413.open-remote-wsl` / `open-remote-ssh` bundled as built-ins (Open VSX VSIXes, versions pinned via `OPEN_REMOTE_*_VERSION` in `build.yml`, mirrored in `build-local.ps1`). They connect to a Null-repacked VSCodium REH server: CI appends the workspace-side built-ins (`null-env`, `null-cpp`, `null-format`, `null-actions`, `null-markdown`, Code Spell Checker) to the stock tarball via `tar @archive` (keeps exec bits) and publishes `null-reh-linux-{x64,arm64}.tar.gz` on the Null release; `release` in the stamped `product.json` is that release's tag. `serverApplicationName` stays `codium-server` (the launcher script inside the tarball), `serverDataFolderName` is `.null-server`. The remote caches a server per VSCodium commit, so a built-in change without a VSCodium bump needs `~/.null-server/bin/<commit>` deleted. Machine-local extensions (`null-tools`, `null-accounts`, `null-music`, `null-startup`, `null-activity`, `null-sync`) declare `extensionKind: ["ui"]`. Not yet verified end to end in a CI-built package; non-tag builds publish no server
- CI builds on `windows-2022`; the developer authors source changes locally
- Releases publish a portable ZIP and an Inno Setup installer to GitHub Releases
- The in-app updater (`null-tools`) checks GitHub Releases on startup and can self-update
- Win11 Explorer context menu provided by a native IExplorerCommand DLL (`shell-ext/`) built with CMake + MSVC

## How the Build Works

The entire build runs in GitHub Actions on a `windows-2022` runner — do **not** try to run it locally.

1. Clone VSCodium at `VSCODIUM_TAG` and VS Code at the matching `MS_TAG`.
2. Apply VSCodium's own patches, then every `patches/*.patch` in name order (`git apply --ignore-whitespace`).
3. Deep-merge `product.json` overlay into `vscode-src/product.json`.
4. `npm ci --prefix extensions/null-markdown` and `npm run build` in it (esbuild bundles the Markdown Editor webview); `npm ci && npm run compile` in each other TS extension (`null-tools`, `null-cpp`, `null-actions`, `null-accounts`, `null-format`, `null-music`, `null-activity`, `null-startup`, `null-env`, `null-sync`).
5. Copy all thirteen built-in extensions into `vscode-src/extensions/`; bundle Code Spell Checker from `CSPELL_TAG`.
6. Replace upstream icons with files from `icons/`.
7. Copy `workbench/custom.css` → `null-custom.css` and `workbench/splash.js` → `null-splash.js` into the source tree; inject `<link>` / `<script>` tags into `workbench.html`.
8. `npm ci && npx gulp vscode-win32-x64` produces `VSCode-win32-x64/`.
9. Build Win11 shell extension: fetch WIL headers, compile DLL with CMake + MSVC, pack and sign sparse APPX (`null-shell-ext.appx`).
10. Stamp version, commit hash, and server URL into the build output's `product.json`; replace letterpress SVGs; `rcedit` the icon into `null.exe`.
11. Build `setup/` with cargo (`cargo test`, then `cargo build --release`); ship `null-setup.exe` as `setup/null-setup.exe` and `install-null-ide.ps1` in `resources/app/null-updater/` (still shipped for Inno and the README install; `null-setup` registers natively).
12. `Compress-Archive` → `null-ide-win32-x64.zip`; Inno Setup → `NullIDESetup-<version>.exe`; both uploaded to the GitHub Release (tag builds) and as workflow artifacts.

## Built-in Extensions
Conventions for every extension with a `src/`:
- `out/` is tracked in git. After editing `src/`, run `npm run compile` in that extension and commit the refreshed `out/` (repo uses `chore: refresh <ext> compiled output` commits). Never hand-edit `out/`.
- `npm test` runs an explicit list of `out/**/*.test.js` files in `package.json`'s `test` script; a new test file is silently skipped until added there.

### null-theme (`extensions/null-theme/`)
Default color theme (Null Dark) via `product.json → defaultColorTheme`. Fonts: Geist Mono, JetBrains Mono, Cascadia Code.

### null-icons (`extensions/null-icons/`)
Built-in file icon theme. Set as the default via `product.json → defaultIconTheme`. Contains SVG icons for a wide range of file types and folder types.

### null-markdown (`extensions/null-markdown/`)
Enhanced markdown preview (GFM, Mermaid, KaTeX, GitHub alerts) on `onLanguage:markdown`, plus the **Markdown Editor** (issue #114): a live-preview `CustomTextEditorProvider` (`null-markdown.editor`; syntax markers hide except around the caret) that is the default view of `.md` files, with a single title-bar button toggling to the plain text editor (Source). `editorProvider.js` is a thin relay over the `TextDocument` (source of truth): the webview mirrors LF text, sends debounced edits with a `baseVersion` that the host applies as one `WorkspaceEdit` and acks, and any host change returns as a full `doc` that the webview diffs in; `syncState.js` (pure) holds the offset/EOL mapping and version rules. Undo/redo is the workbench's (no CodeMirror history). The webview is `webview/editor/*.mjs` (CodeMirror 6 + `@lezer/markdown`, dev dependencies) bundled by `npm run build` (esbuild) into the tracked `lib/editor.js`; `lib/editor.css` is hand-written. `specs.mjs` is the pure decoration plan (tree + selection in, specs out); tables, Mermaid, `$$` math, alerts, HTML and images render as widgets through the host's `createMd()` + `processAlerts()` (`renderBlock`/`rendered` messages). `node_modules` (markdown-it, KaTeX, Mermaid, highlight.js) come from `npm ci --prefix` in CI and are not synced by `sync-local.ps1`; it copies `lib/` and the host files. Design: `docs/specs/null-markdown-editor-design.md`; plan: `docs/plans/null-markdown-editor.md`.

### null-format (`extensions/null-format/`)
Prettier (in-process), rustfmt and clang-format formatting providers. Editable fallback configs are `null-format.{prettier,rustfmt,clangFormat}.defaultConfig`; a project's own `.prettierrc` / `rustfmt.toml` / `.clang-format` always wins.

### null-music (`extensions/null-music/`)
Local-file music player: view `null.musicView` in its own `null-music` activity-bar container (listed in the Features launcher; `null.musicView.focus` reveals it; it shared `null-workspace` briefly but the pane was too short to use), status bar item, `Ctrl+Alt+…` media keybindings. The extension host owns all state — `Library` (folders + `.m3u8`, tags and cover art via the in-house `library/tagReader.ts`, JSON cache in `globalStorageUri`), `Queue` (history-aware shuffle, play next/add), `Player` (single position clock, paused session restore under `globalState` key `null-music.session`) and an `AudioOutput`. Sound comes from an `<audio>` element in the sidebar webview (`WebviewAudioOutput`): commands reveal the view and wait for its `ready`, and closing the view stops playback. `isPlaying` is true only after the output reports `play`. There is no provider abstraction; do not add one. The sidebar UI is vanilla TS in `src/webview/music/` (`module: none`, no imports; `tsconfig.webview-music.json` compiles it into the tracked `lib/music.js`, and `lib/music.css` is hand-written — the only hand-edited file in `lib/`). Pure `dom.ts`/`model.ts` are also compiled by `tsconfig.webview-music-shared.json` so `node --test` can load them through `vm` (top-level `function` declarations only). Host and webview share the typed `HostToWebview`/`WebviewToHost` unions in `protocol.ts` (the host pulls them in with a triple-slash reference); `MusicViewController` publishes `player`/`queue`/`library`/`liked` snapshots and the webview only sends intents. Rows carry `data-vscode-context` and the manifest's `webview/context` menu contributes the `null-music.track.*` commands. `sync-local.ps1` copies `lib/`. Designs: `docs/specs/null-music-engine-design.md`, `docs/specs/null-music-player-ui-design.md`; plans: `docs/plans/null-music-engine.md`, `docs/plans/null-music-player-ui.md`.

### null-activity (`extensions/null-activity/`)
Local-only activity tracking (issue #113; engine, dashboard, git statistics, badges and WakaTime import). Activated on `onStartupFinished`; returns `NullActivityApi` (`getIntervals`, `getDailyStats`, `getProjectStats`, `getLanguageStats`, `getSessions`, `recordActivity`, `start/pause/endSession`, `onDidChange`) from `activate`. Deletion is deliberately not on the API. Everything is derived from an append-only interval log: `intervals-YYYY-MM-<windowId>.jsonl` under `globalStorageUri`, one file per window (random id per extension-host launch, never `env.sessionId`, which all windows of one app launch share) so concurrent windows never clobber each other; `stats.ts` keeps two views: the headline (daily/monthly totals, hourly bars, session durations, dashboard `totalMs`) is the union of all windows, while per-project and per-language numbers sum each window's own time via `attributedIntervals` (a WakaTime import only fills gaps live windows left). `Tracker` is a pure state machine over `Heartbeat`s with an injected clock (close rule: a heartbeat within `idleTimeout` (default 900 s, WakaTime's 15 min) of the last one extends the interval and a closing heartbeat ends it at its own time; closes with no heartbeat — pause, shutdown — end at the last heartbeat, so idle time is never credited); only `heartbeatSource.ts`, `statusBar.ts`, `commands.ts` and `extension.ts` import `vscode`. Heartbeats count whether or not the window is focused (parallel agent windows each extend their own interval) and for edits to any open file or untitled document (agent edits to background files count, attributed to the edited file); terminal activity is shell-integration command start/end (no keystroke API exists). Project key is the normalized git remote (worktree-aware), falling back to the folder path. `null-activity.enabled` is the master switch. The only network code is `gistHttp.ts` (opt-in badge publishing); the engine, dashboard and git code have none. The **Coding Activity dashboard** (`null-activity.openDashboard`; the status bar item opens it) is one reused `WebviewPanel` in `dashboardPanel.ts`, fed by the pure `dashboardModel.ts` (`buildDashboardModel` over `NullActivityApi`, plus `parseWebviewMessage` for untrusted webview messages); the CSP shell is `dashboardHtml.ts`. The vanilla-TS UI in `src/webview/dashboard/` (`module: none`, no imports) compiles via `tsconfig.webview-dashboard.json` into the tracked `lib/dashboard.js`; `tsconfig.webview-dashboard-shared.json` compiles `protocol.ts`/`dom.ts`/`model.ts` for the `vm` tests; `lib/dashboard.css` is hand-written; `tsconfig.json` excludes `src/webview`. `sync-local.ps1` copies `lib`. It is read-only (no delete buttons) and adds no engine API. **Git statistics** (`gitLog.ts` pure parser, `gitStatsService.ts` with injected deps and a 60 s per-repo cache, `gitExec.ts` the only place that spawns git): the dashboard shows your commits, distinct files and lines +/− per project and in total. Only commits whose author email equals the repo's `user.email`, on local branches, no merges, for projects in the *open workspace folders* matched by project key (the interval log stores no folder paths, so other projects show "—"); nothing runs in an untrusted workspace. `DashboardPanel` posts the model at once with cached numbers, loads in the background and posts again; the log, `NullActivityApi` and `ActivityService` are unchanged. **Badges** (`badgeModel.ts` + `badgeSvg.ts` pure: total time, average per active day and top language, flat shields-style SVG; `gistClient.ts` + `badgePublisher.ts` with injected deps and no `vscode`; `badgeCommands.ts` is the `vscode` glue): `null-activity.saveBadges` writes the three SVGs to a folder; `null-activity.publishBadges` publishes them to one secret Gist through null-accounts (`getToken(account, ['gist'], …)`, github.com accounts only) after a one-time consent modal, remembers `{ gistId, accountId, owner, hash }` in `globalState` (`null-activity.badge`) and copies the README Markdown. `null-activity.badge.autoPublish` (default off) only refreshes that Gist hourly with a silent token, skips unchanged content, and does nothing while `null-activity.enabled` is off. **WakaTime import** (`wakatimeImport.ts` pure: `convertExport` turns the wakatime.com export's heartbeats into intervals using the export's own `user.timeout`, 15 min when absent; `languageMap.ts` pure name table; `wakatimeProjects.ts` matches each project to a local git repo through `projectIdentity.repoRoot`, else keeps the WakaTime name; `importCommand.ts` is the `vscode` glue): `null-activity.importWakaTime` writes `intervals-YYYY-MM-import-wakatime.jsonl` through `IntervalStore.replaceWindow` via the internal `ActivityService.replaceImported` (not on `NullActivityApi`), so re-importing replaces the previous import and `deleteRange` / `deleteAll` cover it. All categories count; imported lines are 0. Passing a file URI to the command skips its dialogs (used by `import.spec.ts`). **Multiple machines** (#131): `machineId.ts` keeps a random id in `globalStorage/machine.json` (name from `null-activity.machineName`, else the host name); `IntervalStore.read` tags every interval with `machine` (read-back only, like `window`), so per-project/per-language attribution keys on `machine/window` and WakaTime imports of all machines are pooled; `getMachineStats` (`machineTimes`, imports excluded) feeds a Machines card that shows only with more than one machine. Other machines' months are cached whole under `globalStorage/machines/<id>/<YYYY-MM>.jsonl`; `activityBlob.ts` (gzip+base64 JSONL, one blob per machine and month, `activity__<id>__<YYYY-MM>.enc`) and `activitySync.ts` (injected port, no `vscode`) upload this machine's months and replace changed remote ones, every 10 min through `syncLink.ts` and null-sync's optional `syncActivity` (no `extensionDependencies`); one writer per blob, so no conflicts and no duplicates. Deleting data only affects this machine. Design `docs/specs/null-activity-multi-machine-design.md`. Designs: `docs/specs/null-activity-engine-design.md`, `docs/specs/null-activity-dashboard-design.md`, `docs/specs/null-activity-git-design.md`, `docs/specs/null-activity-badge-design.md`, `docs/specs/null-activity-wakatime-import-design.md`; plans: `docs/plans/null-activity-engine.md`, `docs/plans/null-activity-dashboard.md`, `docs/plans/null-activity-git.md`, `docs/plans/null-activity-badge.md`, `docs/plans/null-activity-wakatime-import.md`. Integration specs: `npm run test:integration` (via `/verify-local null-activity`).

### null-startup (`extensions/null-startup/`)
Startup profiler (issue #19). Activated on `onStartupFinished`. It reads startup data through the internal command `_null.startup.snapshot`, added by patch 010 (`getExtensionsStatus()` / `ITimerService` are not reachable from the extension API); on a build without the patch (stock VS Code) `snapshotSource.ts` logs once and nothing is recorded — the report panel just shows its empty state. `Capture` writes one `Report` right after startup and rewrites it under the same id ~30 s later (extension status is cumulative, so the later snapshot supersedes the first). Milestones: `windowCreated` (`code/didCreateCodeWindow`), `uiInteractive` (`code/didStartWorkbench`), `workspaceRestored` (`code/didRestoreEditors`, the headline; upstream's `startupMetrics.ellapsed` stops at `didStartWorkbench`, earlier), `extensionsSettled` (end of the last eager activation); launch is `code/didStartMain` / `code/willOpenNewWindow` / `code/timeOrigin`. An extension is *deferred* if it ended after `workspaceRestored`. `intervals.ts` (`incrementalImpact`) makes overlapping phases and activations add wall-clock time once. Pure modules: `buildReport`, `intervals`, `compare` (regression = ≥ 50 ms and ≥ 10 %), `exportReport`, `reportModel` (`buildViewModel`, `parseWebviewMessage`), `sanitize` (activation events with paths reduce to their type); only `snapshotSource.ts`, `reportPanel.ts`, `commands.ts` and `extension.ts` import `vscode`. `ReportStore` keeps one JSON per launch+window under `globalStorageUri/reports`, prunes to `null-startup.retention` (default 20) and never reads, rewrites or deletes files that are not current-version reports. The report is one reused `WebviewPanel` (`null-startup.openReport`); the vanilla-TS UI in `src/webview/report/` (`module: none`) compiles through `tsconfig.webview-report.json` into the tracked `lib/report.js`, `tsconfig.webview-report-shared.json` feeds the `vm` tests, `lib/report.css` is hand-written. Commands: `openReport`, `copyReport` (Markdown), `exportReport` (JSON), `clearHistory`; settings `null-startup.enabled`, `.retention`, `.slowExtensionMs` (default 100, a flag not a verdict). Reports hold only extension IDs, sanitized events, timings and the app version. The integration runner uses vanilla VS Code, so `activation.spec.ts` covers only the degradation path; the real command is checked by hand in a patched build. Design: `docs/specs/null-startup-profiler-design.md`; plan: `docs/plans/null-startup-profiler.md`.

### null-env (`extensions/null-env/`)
Environment check (issue #89). Workspace-side (no `extensionKind`), so it checks the machine that has the tools, including a remote window. Pure modules: `detect` (the one manifest → language table; `detectProjects` / `detectLanguages`), `probe` (the one executable finder: PATH with `PATHEXT`, plus `~/.cargo/bin` and LLVM dirs; `findRustfmtPath` / `findClangFormatPath` with configured → bundled → lookup precedence), `rules` (data-only requirement table: `anyOf` extension ids or tool names, `required` / `recommended`, fix = install an extension or open a URL; `debugExtensionFor` maps `lldb`/`cppdbg` to their extension), `check` (`check(languages, probes)` → findings, plus the snooze signature helpers). Only `probes.ts`, `envState.ts`, `fix.ts`, `commands.ts`, `statusBar.ts` and `extension.ts` import `vscode`. `Null: Check Environment` (`null.env.check`) is a QuickPick of findings; the status bar warning shows only `required` findings, can be hidden per workspace and reappears when the missing set changes. `null-format`, `null-actions` and `null-cpp` declare `extensionDependencies: ["null.null-env"]` and use its exports through a local `envApi.ts`, with no fallback (a fallback would be a second copy). `null-cpp.debug.start` calls `ensureDebugType` before `startDebugging`. `null-tools` (UI host) reads findings through the internal command `null.env.getFindings` (exports do not cross hosts) for its dashboard row. `PATH` is read at extension-host launch, so a CLI installed later stays "missing" until restart. Design `docs/specs/null-env-environment-check-design.md`; plan `docs/plans/null-env-environment-check.md`. Integration spec: `npm run test:integration` (via `/verify-local null-env`).

### null-sync (`extensions/null-sync/`)
Cross-device sync (issue #23) of `settings.json`, `keybindings.json` and snippets and the installed-extension list with no server of our own: one secret GitHub Gist per user, reached through null-accounts (`getToken(account, ['gist'], …)`, github.com accounts only) and **encrypted on the device** (AES-256-GCM, scrypt key from a passphrase of at least 12 characters kept in `SecretStorage`; a secret Gist is only unlisted, so it holds ciphertext plus a plaintext `manifest.json` with the KDF parameters). The passphrase cannot be recovered: forgetting it means Stop Syncing and starting a new store. `extensionKind: ["ui"]`, off by default (`null-sync.enabled`), not run in Safe Mode (publisher `null` built-ins are disabled). Pure, injectable modules: `cryptoBox`; `syncPlan` (`planFile(local, remote, base, deletable)`, where `base` is the pair `{ local, remote }` recorded at the last sync because a pulled `settings.json` is not byte-identical to the remote text); `settingsFilter` (`jsonc-parser`, the only runtime dependency; removes `null-sync.excludedSettings` keys — paths, terminal profiles, proxy, anything matching `*token*`/`*secret*`/`*password*`/`*apiKey*`/`*credential*` — before hashing and uploading, and puts this device's values back on pull); `gistStore` (+ `gistHttp.ts`, the only `fetch`); `localFiles` (every name through `isSyncableFile`, atomic writes, backups of the losing version under `globalStorage/null-sync/backups`, last 10 per file); `lock` (cross-window lock file); `enable`; `syncEngine` (`run` / `resolve` / `restore` / `stop`). Only `prompts.ts`, `commands.ts`, `extensionHost.ts` and `extension.ts` import `vscode`. The `activity` category (default **off**, consent modal) has no files in the three-way engine: `syncEngine.syncActivity(exchange)` hands null-activity the `activity__*` Gist files and uploads what it returns (see null-activity). Whole-file three-way sync: one side changed wins; both changed is a conflict that is never auto-resolved; a missing `settings.json`/`keybindings.json` never deletes the remote copy, a deleted snippet does; a file open with unsaved edits is skipped and retried. `extensionSet` merges the installed-extension IDs by set arithmetic (never a conflict); `extensionHost.ts` reads them from `~/<dataFolderName>/extensions/extensions.json` so disabled extensions count, and an unreadable file skips the extension sync instead of reading as 'all uninstalled'. Only interactive runs install; removals are only reported (`pendingRemovals`) until `uninstallRemoved(id)`. Background runs (startup + 10 s, 30 s after a change, every 10 min) never prompt. **No UI:** `activate` returns `NullSyncApi` (`getStatus`, `onDidChangeStatus`, `syncNow`, `resolveConflict`, `uninstallRemoved`) and the `null.sync.*` commands include `null.sync.showStatus`; the Null workspace rework will build the Sync screen on that contract. Design `docs/specs/null-sync-design.md`; plan `docs/plans/null-sync.md`. Integration spec: `npm run test:integration` (via `/verify-local null-sync`).

### null-actions (`extensions/null-actions/`)
Status-bar buttons that run shell commands (via a dedicated, deterministically-reused terminal per button — identity is keyed by button id, never by command text, so window reloads and folder reopens don't spawn duplicate terminals) or VS Code API commands. Configured through a settings panel opened via the `$(gear) Actions` status bar item or the `null-actions.openSettings` command (opens as a `WebviewPanel` in the main editor area, not a sidebar view), or directly via the `null-actions.buttons` setting. Shell buttons run through terminal shell integration (`TerminalHost.execute`; falls back to `sendText` when it is absent, waiting up to 3 s on a just-created terminal): the button shows a spinner while running and `$(check)`/`$(error)` plus duration for 8 s after (exit code in the tooltip; clicking a failed result reveals its terminal). Clicking a still-running button follows the per-button `onBusy` setting (`ask` default, `restart` = Ctrl+C then re-run, `show`, `run`); requires VS Code 1.93+. A button with a `problemMatcher` (a matcher name such as `$tsc`, `$eslint-stylish`, `$gcc` or the bundled `$null-rustc`; `$rustc` itself only exists with rust-analyzer installed) runs as a `vscode.Task` (`TerminalHost.runTask`, `ShellExecution`, dedicated panel) instead of the terminal path, so errors reach Problems and clear on the next run; state, exit code and `onBusy` work the same (restart terminates the task, show finds the `Task - Action: <label>` terminal). Only matcher *names* work: the Task API takes no inline matcher objects. Cargo and npm suggestions get matchers by default (npm: `tsc`/`eslint` in the script body). Integration spec `problemMatcher.spec.ts` (`npm run test:integration`, loads null-env too). Supports variable substitution (`${workspaceFolder}`, `${file}`, `${selectedText}`, etc.), priority-ordered status bar placement, an Affinity-style canvas color picker for the button text color, and project-type-detection suggestions (`Cargo.toml`, `CMakeLists.txt`, `*.csproj`, or a one-click "Load npm scripts" button that writes each `package.json` script in as a real persisted button). See `docs/specs/null-actions-design.md`.

### null-accounts (`extensions/null-accounts/`)
GitHub/GitLab account manager (issue #102). Activated on `onStartupFinished`; exports `NullAccountsApi` (`getAccounts`, `getAccountForFolder`, `ensureAccountForFolder`, `getToken`, `onDidChange`) via `extensions.getExtension('null.null-accounts')?.exports`. Account metadata lives in `globalState`, secrets in `SecretStorage` under `null-accounts/<id>`; `Account.host` is a bare lowercase hostname. `getToken(account, scopes?, { interactive? })` is silent unless `interactive` is true. The GitHub provider wraps VS Code's built-in `github` session (`Account.externalId` is the session's account id; tokens stay with VS Code). GitLab accounts (gitlab.com and self-hosted) sign in through an OAuth device flow (`providers/gitlabOAuth.ts` protocol, `providers/gitlab.ts` provider): tokens live in `SecretStorage` as one JSON string, refresh is single-flight, and an account whose sign-in was refused is flagged "needs re-auth" (Accounts panel button + one-time notification). The OAuth application ID comes from `null-accounts.gitlab.clientId` (gitlab.com, shipped default) or `null-accounts.gitlab.hostClientIds` (self-hosted); both are application-scoped settings. Servers that disallow user OAuth apps use a personal access token instead ("GitLab with an access token…"): validated against `/user`, stored raw in `SecretStorage`, `authMethod: 'https'`, never refreshed. Binding a folder wires git (`gitPlan.ts` → `gitWiring.ts` for repo-local `user.name` (the account's optional `gitName`, else its username) / `user.email` / `credential.https://<host>.username` / `core.sshCommand`, `gitCredentials.ts` for the token in the OS credential store via `git credential approve|reject`): it reconciles against the bindings on every change, every refreshed token and every 5 minutes; unbinding restores the values it replaced; global git config is touched only by the Accounts panel's "Set as global git identity" button (`globalIdentity.ts`: `user.name` / `user.email`). SSH-key accounts (Add Account → "SSH key…", for servers such as a university GitLab; `sshAccount.ts`) have no token — `api.getToken` returns `undefined` for them — and are tested once with `ssh -T` when added (`sshCheck.ts`); a failed test warns but still saves. Folder→account bindings live in `globalState` (`projectBinding.ts`). One account can be the default (`null-accounts.defaultAccount`, a switch on its Accounts-panel card): `defaultAccount.ts` binds each open folder that has never had an account to the account matching its origin remote, else to the default — once per folder (`defaultAdopted`), so "use no account" sticks. Profile pictures (`avatars.ts`): fetched once per account from github.com (`/<user>.png`) or the account's GitLab host (`/api/v4/users?username=`), kept as small `data:` URIs in `globalState` (`null-accounts.avatars`) and used by the panel (CSP `img-src data:`), the Accounts menu and the activity-bar button; a missing picture falls back to the initial. The panel tab icon is `media/accounts-{light,dark}.svg`. The Accounts menu (activity-bar avatar) is published as the context key `null.accounts.menu` (`ui/accountsMenuController.ts`) and rendered by patch 007. SSH keys (design `docs/specs/null-accounts-ssh-keys-design.md`): any account may carry a private key (`sshKeyPath`; required for `ssh` accounts, which have no token), shown in the Accounts panel with its fingerprint (`sshKeyOps.ts`, `ui/keyActions.ts`, `ui/keyInfo.ts`). Null IDE generates passphrase-less ed25519 keys under `~/.ssh/null-accounts/` (`generateKey`; only keys inside that folder are ever deleted — `isManagedKey`), uploads the public key through the account's token (`keyUpload.ts`: GitHub `write:public_key` + `write:ssh_signing_key`, GitLab `api`; a token-less account copies it and opens the server's key page instead), and `signCommits` writes `gpg.format=ssh` / `user.signingkey` (the private key path) / `commit.gpgsign` into the repo after `canSign` proves the key signs with no prompt. There is no ssh-agent or passphrase support. So that plain `git clone` and other tools find the key too, `sshConfig.ts` keeps `~/.ssh/null-accounts/config` (one `Host` block per hostname, `IdentitiesOnly yes`) in line with the accounts and adds a single marked `Include null-accounts/config` line at the top of `~/.ssh/config` (removed again when no account has a key). Integration spec `signing.spec.ts` makes a real signed commit. Designs: `docs/specs/null-accounts-design.md`, `docs/specs/null-accounts-menu-design.md`; phase plans: `docs/plans/null-accounts-phase*.md`.

## Installer and Scripts

### `scripts/install-null-ide.ps1`
- Installs from a GitHub Release (latest by default) or a local ZIP (`-ZipPath`)
- Per-user install to `%LOCALAPPDATA%\Programs\Null IDE` — no administrator elevation required
- Creates desktop and Start Menu shortcuts, plus a Start Menu shortcut `Null IDE (Safe Mode)` (`--safe-mode`)
- Registers "Open in Null" and "Open Folder in Null" context menu entries in `HKCU`
- Adds the install directory to the user's `PATH` (so `null .` works in new terminals)
- Seeds default settings into `%APPDATA%\Null\User\settings.json`
- Writes `.null-ide-install.json` (repo, version, timestamp) for the in-app updater

### `setup/` (null-setup)
`null-setup.exe` lives at `<installDir>\setup\null-setup.exe`. Modes: `prefetch` (headless download + SHA256 verify into `%LOCALAPPDATA%\Null\updates\<tag>\`, JSON progress lines on stdout), `update` (progress window; relocates itself out of the install dir, closes the IDE, journaled swap with rollback, re-applies registrations through `install-null-ide.ps1 -ReapplyRegistrations -NoElevate`, waits for the new IDE's `.null-ready` marker), `recover` (finishes or rolls back an interrupted swap from `<parent>\.null-update-journal.json`). `update` never elevates. `NULL_SETUP_API_BASE` redirects the GitHub API for tests (`scripts/fake-release.mjs`). Core logic and its tests are in `setup/core` (`cargo test -p null-setup-core`). Design `docs/specs/null-setup-installer-design.md`; plan `docs/plans/null-setup-updater.md`.

Installer engine (sub-project 2a, headless CLI only, no window yet): `install --version <tag> --install-dir <dir> [--config <file>]` (refuses an existing install and a non-empty folder), `repair` (reinstall the installed version), `modify --config <file>` (registrations only → no swap and the IDE keeps running; a changed built-in set → repair with the new config) and `uninstall [--delete-data]` (keeps `data\` and `%APPDATA%\Null` unless asked; never touches a folder without `.null-ide-install.json`). All four go through the `update` pipeline (`update::Kind { Install, Update, Repair }`) or `manage`, print JSON progress lines, and `--force-close` ends IDE processes that ignore the close request. `<install>\install-config.json` (`install_config.rs`: shell-integration `Feature`s plus `excludedBuiltins`) is read by `update`, so updates honor the saved choices (an exclusion the new release cannot honor lapses with a log note; a corrupt or newer-schema file stops the update before anything is extracted). `<install>\builtins.json` is generated by `scripts/gen-builtins.mjs` from `setup/builtins.config.json` plus each extension's `package.json` and shipped in the zip and as a release asset; excluded built-ins are deleted from the staged tree before the swap (core ones are locked, dependencies via `requires` stay). Registrations are native (sub-project 2b, `setup/core/src/shell/`): `Registrar` (injected through `Opts`, `UninstallOpts` and `modify_in_place`, so tests never write the registry) → `shell::apply_with(loc, sys, …)` over a `Locations` (HKCU prefix + Desktop/Programs folders; tests use a scratch hive) and a `System` trait (Explorer, change broadcasts, `.lnk`, certificate store, APPX; faked in tests, `WinSystem` for real). The Win11 sparse APPX still goes through the three `*-AppxPackage` PowerShell cmdlets; the elevated certificate import is `null-setup trust-cert --install-dir <dir>` (reads only `<dir>\shell-ext\NullIDECert.cer`, requires `.null-ide-install.json` and subject `CN=Null IDE`). `install-null-ide.ps1` is no longer called by `null-setup` but is still shipped for Inno and the README one-liner until 2c deletes it with Inno. Only `install` and `modify` may elevate. Plan `docs/plans/null-setup-registrations.md`; runbook `docs/specs/null-setup-registrations-runbook.md`. Run the four modes from a copy outside the install: started from `<install>\setup
ull-setup.exe` the process relocates itself and exits 0 at once, so the caller sees neither the result nor the exit code (the relocated copy cannot be waited for, a handle on the original would block the swap). Plan `docs/plans/null-setup-installer-engine.md`; pruning check `docs/specs/builtin-pruning-check.md`; runbook `docs/specs/null-setup-installer-engine-test-runbook.md`.

First-run hand-over (sub-project 2c-1): `builtins.json` also carries a `settings` table (the seven keys the wizard may preset: `workbench.colorTheme`, `editor.fontFamily`, `editor.fontSize`, `files.autoSave`, `editor.formatOnSave`, `window.menuBarVisibility`, `null.updates.check`) and a `marketplace` table (empty); both come from `setup/builtins.config.json`. `install --first-run <abs file>` (install only) checks the choices against the installed package's `builtins.json` (`first_run::validate`) and writes `%APPDATA%\Null\null-setup\first-run.json`; nothing is written for an invalid or empty set. null-tools consumes it once (see its table). Plan `docs/plans/null-setup-first-run.md`; check `docs/specs/null-setup-first-run-check.md`.

## Patches

Workbench chrome customisations (CSS/JS injection, icon swaps) are handled by direct file injection rather than patches — that proved fragile across VS Code version bumps. `patches/` is for changes that must touch VS Code's own source (a workbench.ts startup hook, a type fix upstream doesn't ship):

- `001-jumplist-recent-projects.patch` — sources the Win taskbar jump list's Recent Projects from null-tools
- `002-fix-claude-copilotapi-types.patch` — restores Anthropic SDK typing in `copilotApiService.ts`
- `003-null-dashboard-startup.patch` — opens the Null Dashboard on startup
- `004-null-dashboard-help-welcome.patch` — wires the dashboard into Help > Welcome
- `005-claude-code-command-center-button.patch` — restores the icon and chevron on the command-center Claude split button
- `006-settings-toc-split-extensions.patch` — splits the Settings editor's Extensions node into Null / Installed Extensions / Built-in Extensions sections
- `007-accounts-menu-null-accounts.patch` — the Accounts menu lists null-accounts' accounts (read from the `null.accounts.menu` context key, each row with its round `data:` picture or provider glyph, the host dimmed after the name, and a "Project: <folder>" heading) and drops VS Code's provider-session and Settings Sync / Copilot / Edit Sessions / tunnel rows; the activity-bar Accounts button shows the picture under `null.accounts.avatar`
- `008-git-commit-message-check.patch` — `smartCommit` calls `null.commitMessage.check` (null-tools) and aborts with its reason; no-op when null-tools is absent
- `009-safe-mode.patch` — `--safe-mode`: the enablement check disables user extensions and Null-owned built-ins (`isDisabledInSafeMode`); core status bar item, `[Safe Mode]` title suffix and Restart in Safe Mode / Restart Normally commands; `reload({ safeMode })`; main-process failed-start counter (`safe-mode-state.json`, offers safe mode after 3 failed starts). Pure parts have `node --test patches/test/*.test.mjs`. Design `docs/specs/safe-mode-design.md`
- `010-startup-snapshot.patch` — stamps extension activations (`activationStartedAt` / `activationEndedAt`) and registers the internal command `_null.startup.snapshot` for null-startup; the pure builder is covered by `node --test patches/test/*.test.mjs`

To add a patch against the VS Code source:
```bash
cd vscode-src
# Make the change, commit it
git add -p && git commit -m "feat: describe change"
git format-patch HEAD~1 -o ../patches/
```

Patches apply **after** VSCodium's own patches, against the VS Code commit at `MS_TAG`. When rebasing to a new upstream, re-export with `git format-patch`.

## Updating the Upstream Version

1. The separate `.github/workflows/upstream-check.yml` workflow (Mondays 06:00 UTC, or manual dispatch) opens a PR automatically if VSCodium has a new release (needs repo setting Actions → "Allow GitHub Actions to create and approve pull requests"). The PR body says whether all patches apply against the new MS tag; a failing check opens it as a draft.
2. To bump manually: edit the root `VSCODIUM_TAG` file (or pass `vscodium_tag` when dispatching `build.yml`).
3. Verify any patches in `patches/` still apply cleanly against the new MS tag.

VSCodium trails VS Code by several releases, so the same workflow's `vscode-releases` job also opens a *Review VS Code 1.x release notes* issue for each VS Code stable release after `Last reviewed` in `docs/vscode-tracking.md` (#115). `/vscode-watch` triages those (Backport / Adapt / Wait / N/A) into that tracker; a bump PR asks you to reconcile rows up to its `MS_TAG`.

## Scope Constraints

- Work only inside `D:\Coding\Apps\null-ide\` and its subdirectories.
- Do not touch system PATH, registry, or any existing VS Code/VSCodium installation outside this repo's installer scripts.
- Full builds normally run in GitHub Actions, not locally. `scripts/build-local.ps1` is the exception: it mirrors the `build-windows` job for iterating on `build.yml`, `shell-ext/`, `installer/`, or the VSCodium/VS Code patch/merge steps — things `scripts/sync-local.ps1` can't reach. Don't run it without being asked; it takes tens of minutes and needs Node, Rust, CMake, VS2022, and Inno Setup 6 installed (see the script's header for the full list).
- Iterate locally with `scripts/sync-local.ps1` (pushes compiled extensions + workbench assets into an installed Null IDE), then `scripts/reload-local.ps1` — `Developer: Reload Window` still serves cached `null-custom.css` / `null-splash.js`. The `/verify-local` skill chains both with the integration specs.
- Do not set the Microsoft extension gallery env var silently; document it in the README only.
